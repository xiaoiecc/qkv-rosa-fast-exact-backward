# 随机化不必改变梯度：精确覆盖查询与稀疏根表

[English](exact-randomized.md) · [普通训练接入](native-training.zh-CN.md)

本轮固定的随机化方案是**精确的随机覆盖查询**。随机性用来改变检索布局，
筛掉远处的无关字符对；所有可能的一位修复仍被完整找到。它不抽掉梯度坐标，
不使用概率指纹冒充字符相等，也不改变选中的联合块。

`randomized=True` 打开这项精确加速。`False` 直接枚举所需位并查完整词。
两种方式共享后面的稀疏根表、匹配状态和数值累计。固定其他种子与输入，开关
改变计算工作，不改变一阶或对角联合信用的数学定义。

## 1. 先问：能不能只改好抽样概率？

上一轮把信用写成共同删除项与修复残差 $`C_{s,j}=B_s+R_{s,j}`$，保留 B 精确，
抽取完整修复通道。这避免了在 K 候选的 max 内抽样，但噪声仍然很大。

这次先给“重要性抽样能救它”一个很宽松的条件：假设已经免费知道每条通道的
完整残差能量 $`E_j`$。在期望预算 $`b`$ 下，最优边缘概率满足

```math
\min_{0\lt p_j\le1,\;\sum p_j\le b}
\sum_j E_j\left(\frac1{p_j}-1\right),
\qquad
p_j=\min\left(1,\frac{\sqrt{E_j}}{\lambda}\right).
```

实际诊断当然不是免费的：先计算全部信用，再求这个 oracle 上限。

| 输入 | 预算 | 均匀抽样相对 RMS | 最优概率相对 RMS |
|---|---:|---:|---:|
| 随机 T=8,192、D=8 | 4 | 84.716% | 84.712% |
| 随机 T=8,192、D=16 | 8 | 70.412% | 70.274% |
| 64 位槽、8 位词表 | 4 | 34.166% | 34.165% |

原因是这些输入的通道能量本来就接近均匀。甚至额外免费提供每个 owner 在全部
通道上的精确均值作为控制变量，前两行的最优残差误差仍有约 66–67%。这否定了
在这批状态上“只把抽样权重调聪明一点就近乎无损”的设想，并不证明所有有误差
的随机方案都不可能。原始定义与结果见
[native_random_noise_ceiling.json](../research/results/native_random_noise_ceiling.json)。

因此本轮的公开随机化开关采用精确查询，默认训练不启用修复通道抽样。

## 2. 原来的根查询在浪费什么

相同 Q 词已经共享根查询，但对每个不同 Q 词 x，仍要逐位问：

```math
x\mathbin{\mathrm{xor}}2^j\in K\;?
```

不同 Q 词数为 $`U_Q`$ 时，这需要 $`U_QD`$ 次完整词查找。
对于稀疏的 64 位词表，绝大多数答案是“不存在”。更糟的是，之前把这些不存在
的答案也存成了稠密表，扫描每个 Q 位置时再次遍历一批空槽。

所以要分别处理两个问题：怎样少问一些肯定无用的问题，以及怎样不把空答案
存下来再读一遍。

## 3. 把位随机分块，为什么不会漏掉任何一位邻居

把 D 个位随机打乱，均衡分成 p 个互不相交的块。实现只考虑 p=2 或 p=4。
对每个块 b，把 K 词按照**块外全部位**建立完整键字典。

如果两个词只差一位，而这一位属于 b，那么它们在 b 之外必定完全相同。
因此它们一定出现在 b 的同一个桶里；在其他块的字典里，这一不同位仍被保留，
所以不会相撞。一位邻居恰好被一个块覆盖。

查询桶后仍比较完整 XOR：只有差异是非零的二次幂，才是需要的邻居。
哈希碰撞靠完整投影键比较解决；投影桶中的远邻靠完整 XOR 排除。
随机性只改变会碰见多少远邻，正确性不依赖它们“碰撞概率很低”。

![八位示例：遗漏不同位所在的块仍能找到邻居，完整 XOR 验证与桶枚举上界](../images/exact-randomized-root-join.svg)

图中不同的是第 4 位，它属于 A。省去 A 后，两边的键都是 `0100`；省去 B 则
保留了这一差别，得到 `1110` 和 `1010`。这个小例子说明覆盖关系。对于建索引
不划算的小输入，规划器仍可以直接查询。

对固定 p、均匀随机分块，若两个词相差 h 个位，只有这 h 位全落入同一块时，
它们才会进入某个共同桶。块大小为 $`m_b`$ 时，h>0 的概率为

```math
\Pr[\text{进入某个共同桶}]
=\frac{\sum_b {m_b\choose h}}{{D\choose h}}.
```

h=1 时概率严格为 1。等大分块时，h≥2 的概率至多 $`p^{1-h}`$。
远邻通常被随机布局分散，有用的一位邻居永远保留。这个概率公式针对固定 p；
实现还会选择 p，不能把数据相关的选择当成固定 p 的均匀分布。

## 4. 遇到很挤的桶怎么办

不让桶大小决定最坏成本。设当前块需要检查 m 个位，桶里有 c 个不同 K 词：

- c≤m：枚举桶内词，逐一检查完整 XOR。
- c>m：直接枚举这 m 个 bit 翻转，查完整词字典。

一条查询在所有块上的候选工作至多

```math
\sum_b\min(c_b,m_b)\le\sum_b m_b\le D.
```

这条上界与数据分布、随机种子都无关。K 高度相关或位分得不好时，桶内枚举
不会无界膨胀。两个分支是同一个覆盖查询的逐桶成本选择，没有按 benchmark
输入名字识别并切换算法。

建索引本身也要付钱。实现用 $`U_Q`$、不同 K 词数 $`U_K`$、K 的变化位、
Q/K 完全相同的比例，粗估直接查询、两块覆盖和四块覆盖的工作。估计包含建桶、
查询、成员检查和固定启动成本，收益不够就使用直接查询。
这个模型只是性能启发式，不承担精确性证明。稠密 D=8、部分稠密 D=16，以及
很小的输入，经常会直接查询。

## 5. 查到了什么，就只存什么

每个 Q 词保存一个 64 位邻居掩码、一个 CSR 起始偏移，以及紧凑的 int32 根目标。
目标按 bit 升序排列，因此后续 repair 的出生顺序与原算法完全一样。

如果某个 K 词第一次出现已经不早于该 Q 词最后一次出现，这条根边永远不可能
因果有效，连紧凑表也不写。扫描时再检查当前 t 的因果限制。

每个查询临时使用一个未初始化的 `targets[64]`；只有已经写入掩码的位才会读取。
没有偷偷保留一次 D 大小的清零。也不需要为每个 Q 词建立一个小对象或排序。

设实际保存的因果根邻居数为 R。根表从 $`O(U_QD)`$ 变为 $`O(U_Q+R)`$ 存储；
含位置到 Q 类的映射则为 $`O(T+U_Q+R)`$。扫描时的根访问由 $`TD`$ 上界变为

```math
\sum_{t=0}^{T-1}\deg(\mathrm{class}(Q[t])).
```

这是根准备和出生扫描的改善。输出张量本身仍有 $`TD`$ 项，完整反向还存在
删除区间、活动修复和数值走廊等成本，不能由此宣布整个反向变成线性。
向量预留容量和其他索引也占内存，记录的 R 不是峰值 RSS。

旧计数器 `root_repair_entries` 保留逻辑查询数 $`U_Q\times\text{请求位数}`$ 的含义，
便于旧接口兼容。新诊断单独记录 `stored_root_entries`，不把两者混用。

## 6. 完整反向实测

基线是上一轮交付提交 `f6d7c4b`。本轮 off/on 都已经使用同一稀疏根表，on 另启用
精确覆盖查询。每行 11 次交替测量，单核 CPU，固定输入；使用预分配输出缓冲区。
计时包含全部原生索引构建与信用累计，不含 Python 验证、投影、优化器、编译和预热。

| 输入 | 上轮完整原生反向 | 本轮 off | 本轮 on | 上轮 / on |
|---|---:|---:|---:|---:|
| 随机 T=8,192、D=32 | 11.624 ms | 11.351 ms | **7.121 ms** | **1.63×** |
| 64 位词，植入一位修复，T=8,192 | 21.824 ms | 20.094 ms | **12.033 ms** | **1.81×** |
| 同上，对角成本 | 18.437 ms | 16.659 ms | **10.435 ms** | **1.77×** |
| 随机 T=2,048、D=16 | 1.756 ms | 1.605 ms | 1.518 ms | 1.16× |
| 随机 T=8,192、D=8 | 26.656 ms | 26.835 ms | 23.974 ms | 1.11× |
| 64 位槽、8 位词表，T=8,192 | 44.476 ms | 39.129 ms | 43.731 ms | 1.02× |
| 周期 T=4,096、D=4 | 47.999 ms | 45.635 ms | 49.376 ms | **0.97×** |

十五行完整矩阵的上轮/on 速度比为 **0.972–1.814×**，包括回退。
不能把没有改变工作计数的 D=8 或周期行的抖动解释为算法收益。
同一批测量中 off/on 比值也有低于 1 的行；原始样本全部保留。

64 位植入修复一行的 SAM 准备由 off 的 **7.960 ms** 降到 on 的 **1.713 ms**。
524,288 次直接根查找变成 16,384 次桶查询和 2,048 个桶成员检查；
实际只需存 2,048 个因果根目标。所有输出仍与基线逐位相同。

原始矩阵、每次种子、工作计数与加载二进制哈希：
[exact_randomized.json](../benchmarks/results/exact_randomized.json)。
测试在计时结束后又增加了四块覆盖与抽样轨迹用例；生产 C++ 未变化。
实际计时用的 C++ 探针已保留，测试文件与生产源文件的哈希区别记录在
[exact_randomized_provenance.json](../benchmarks/results/exact_randomized_provenance.json)。
这是完整**信用引擎**的时间，不是整个模型训练吞吐；普通组件的端到端结果见
主报告。

## 7. 验证和复现

`tests/test_randomized_join.py` 比较开关两边的全部 Q/K/V 信用、长度、路线和
原来的 23 个结构计数，覆盖空流、最高位、不同位宽、相关词表、两块/四块/直接
三种计划以及多个种子。既有修复抽样的期望/方差、强制通道和哈希布局检查继续通过。
正式计时还与冻结的上一轮引擎逐位比较，源文件在计时期间未变化。

```bash
python -m unittest tests.test_randomized_join tests.test_repair_sampling tests.test_backward_hash
python benchmarks/exact_randomized.py --baseline-root /path/to/frozen-previous-source --cpu 0
```

基线目录仅用于研究比较，不进入生产运行时。概率抽样的旧研究接口仍有明确误差
合同，但不由 `randomized=True` 启用。

## 与已有方法的关系

用多个子码索引进行精确 Hamming 搜索有明确的既有研究，例如
[Norouzi、Punjani、Fleet：Multi-Index Hashing](https://arxiv.org/abs/1307.2982)；
随机布局同时保证近邻不漏检，也与
[Pagh：CoveringLSH](https://arxiv.org/abs/1507.03225) 的目标相关。
这里使用的是半径 1 的简单覆盖构造，结合逐桶 D 上界、因果根认证与稀疏出生表，
来消除这个 ROSA 引擎的具体重复工作。没有宣称重新发明通用近邻搜索。
